# EAF 2.0 P0 实现进度

更新：2026-10-16。总体设计见 [设计与分阶段计划](../superpowers/specs/2026-10-16-eaf-2.0-design.md)。

## 已实现：持久化消息同步

- 复用 V2 store 的会话版本号，写盘完成后发布消息变更，接入 Electron IPC 与 Web SSE。
- 快照和实时消息使用同一版本体系；忽略重复与过期变更，版本缺口、历史替换和重连触发有界快照恢复。
- 刷新结果不会按客户端时钟覆盖更新的消息；分页拒绝混入其他版本的数据。
- Codex 的流式文本、commentary 和工具过程实时持久化；版本化会话由服务端返回实际消息，不再依赖前端临时消息匹配。
- 持久化前固定消息内容，防止调用方在等待磁盘写入时修改同一个对象；修复崩溃恢复后快照内容与版本不一致的问题。

目前采用“持久化版本 + 快照补齐”，尚未提供按游标逐条重放历史 SSE 事件。

## 已实现：常驻服务与操作防重

- 桌面与 Web 共用独立设备服务，通过带本机密钥的管道/Unix socket 连接；关闭窗口或 Web 网关只断开客户端，CLI 留在服务内继续运行。
- 操作 ID 在执行前落盘；并发重复请求共用结果，确认丢失和界面重载继续使用原 ID。服务重启后未确认的操作标记为待确认，不自动重跑。
- 重试返回最新目录数据，避免旧操作结果覆盖后来创建的项目/会话；操作日志在执行前保存原始输入，结果中的目录副本压缩为稳定身份。
- 增加 `npm run service:status`、`npm run service:stop`；有任务或操作运行时拒绝停止服务。`npm run smoke:providers` 在隔离的 EAF 数据目录中执行真实 CLI 冒烟测试。

## 实测发现与修复

真实 Codex 测试发现：回复已完成，但原生导入把 EAF 消息 ID 替换为文件行号 ID，导致刷新后无法关联回复。现已持久化会话历史归属：EAF 接管后的历史由运行时维护，自动导入不能替换消息；重启后归属保持，重叠项目也不重复导入同一受管会话。

这意味着受管会话在外部 CLI 继续执行后，暂不自动覆盖 EAF 历史；显式交接/恢复入口仍需补齐。尚未被 EAF 接管的原生会话继续正常导入。

## 提前完成的 P1：模型自动更新

- 从 Claude `initialize` 和 Codex `model/list` 获取目录；启动、每 15 分钟和手动刷新更新列表，CLI 版本变化触发刷新。按设备、工作区和本机登录配置签名隔离缓存，失败时保留上次结果。
- 新建空会话采用运行时推荐的完整模型 ID；已有会话保留原 ID，原生别名由 CLI 解析。模型和推理档位不再依赖界面里的固定版本名单。
- Claude 斜杠命令一并读取初始化结果，不再通过生成一次“OK”回复探测。刷新显示更新时间与缓存状态。
- 运行时自身未提供的模型仍需先由 CLI 支持；EAF 会自动读取升级后的目录。

## 已实现：群聊连续发送与停止

- 首条不带 `@` 的消息交给首个启用成员；后续默认交给最近完成回复的成员。界面显示默认接收者，提交时固定目标；指定不可用成员会明确报错。
- 在 CLI 输出前绑定群聊消息与实际回复 ID；同一 Codex 成员按顺序执行，其他成员独立运行。停止会取消尚未执行的任务，并处理准备中、启动确认尚未返回的情况。
- 每次提交固定已完成的公开群聊上下文，限制旧上下文大小；不会把工具过程或半截回复当成共享结论，也不会漏掉稍后才完成的早期回复。
- 群聊运行状态包含尚未结束的提交数，某个成员先结束不会清掉其他任务的运行提示；重连快照也包含排队状态。
